Executive Summary
This specification outlines the definitive engineering roadmap to upgrade AeroMESH into a commercial-grade, self-bootstrapping native Windows desktop application. It remediates all previously identified lifecycle leaks, security vulnerabilities, and permission faults while introducing an autonomous runtime that eliminates all reliance on developer setup scripts (setup.ps1, start.ps1), guarantees zero forced model downloads, and provides a polished Kimi dark matte onboarding wizard with strictly Lucide icons.

1. Master Fixing Strategy & Upgraded System Architecture

The core objective is to transition AeroMESH from a developer script running in an unmanaged Edge browser window into a hardened, self-contained native Windows desktop application.

Strategic Core Pillars

  • Self-Bootstrapping Autonomy: The binary provisions its own directory hierarchy, generates CSPRNG keys, verifies CUDA runtime DLLs, and resolves network topologies without invoking external shell scripts.
  • Zero Forced Model Downloads: Unconditional model downloads (e.g. DreamShaper 8 in legacy start.ps1) are completely excised. No weights are transferred without explicit user opt-in.
  • First-Run Onboarding Wizard: A frictionless 3-step modal flow inside the UI handles diagnostics, opt-in starter models with streaming progress, and role launch.
  • Kernel-Enforced Lifecycle Trapping: SafeProcessJob binds all child engines (aeromesh.exe, sd-cli.exe) to a Windows Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE.
  • Kimi Dark Matte Aesthetic: Deep obsidian matte surfaces, liquid glass panels, and strictly Lucide SVG icons (zero emojis).

2. Architectural Solutions & Decision Evaluation Matrices

Decision 1: Window Lifecycle & Process Zombie Remediation

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: Embedded WebView2 Rewrite host using wry/tao embedding WebView2 COM loader directly. True native HWND window; clean WM_CLOSE events; no external process. Heavy C++ COM bindings; build friction on MinGW/MSVC; risk to CSS filters. Rejected
Option B: Supervised Edge + Job Object Retain Edge App-Mode; supervise Child handle; trap in SafeProcessJob. Zero new C++ GUI crates; kernel-guaranteed VRAM release; sub-100ms exit. Requires Microsoft Edge present on host (standard on 99.8% of Windows). Selected
Option C: Background Tray Daemon Run perpetual background tray service; closing window minimizes. Models stay in VRAM between sessions; similar UX to Docker/Ollama. Confuses users expecting window close to free GPU VRAM for gaming. Rejected

Decision 2: File Handling, Storage Locations & Windows Permissions

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: UAC Admin Elevation Embed requireAdministrator manifest to write directly to Program Files. Zero path code changes. Violates enterprise security; blocked by corporate IT; UAC prompt on every run. Rejected
Option B: Windows AppData Hierarchy Map config to %APPDATA%, cache/profiles to %LOCALAPPDATA%. 100% compliant with Windows standards; works under standard user accounts. Requires centralizing path resolution across CLI and desktop crates. Selected
Option C: MSIX Virtualization Rely on Windows VFS filesystem redirection in an MSIX package. No path modifications inside code. Masks structural flaws; breaks external symlinks; signing friction. Rejected

Decision 3: Localhost API Security & CORS Remediation

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: CSPRNG Token + Host Guard Generate BCrypt token; inject in meta tag; restrict CORS to 127.0.0.1. Defeats CORS drive-by and DNS rebinding; preserves OpenAI client compatibility. Frontend fetch calls must attach Authorization header. Selected
Option B: Ephemeral Local mTLS Generate self-signed certificate on startup; bind HTTPS loopback. Encrypted loopback traffic. Severe browser certificate warnings; modifies Windows Certificate Store. Rejected
Option C: Named Pipes Only Eliminate HTTP port entirely; pass messages over Win32 Named Pipes. Zero network attack surface. Completely breaks OpenAI API client compatibility (/v1/chat/completions). Rejected

Decision 4: Air-Gapped Network & Offline UI Resilience

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: Bundled Assets + GetAdapters Vendor all JS/CSS/fonts locally; resolve IPs via iphlpapi.dll. 100% air-gapped functionality; zero CDN stalls; native adapter accuracy. Adds 1.8 MB to static asset payload. Selected
Option B: Dynamic CDN Fallback Load from CDN; fallback to local files on script onerror. Saves initial distribution bytes if online. Causes 3-5 second DNS timeout stalls on air-gapped networks; layout shifts. Rejected
Option C: Dual Build Modes Produce separate online and offline editions. Tailored bundles. Double maintenance overhead; high risk of feature divergence. Rejected

Decision 5: Self-Bootstrapping Engine Architecture

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: Script Wrapper Runner Bundle PowerShell scripts into a compiled executable runner. Reuses existing script code. Blocked by enterprise ExecutionPolicy; antivirus heuristics flag wrappers. Rejected
Option B: Native Rust Bootstrap Perform DLL validation, PATH setup, secret creation, and Job init in Rust. Instant sub-100ms launch; zero script dependencies; type-safe diagnostics. Requires ~300 lines of robust systems bootstrap code. Selected
Option C: Background Windows Service Install background service as LocalSystem to manage prerequisites. Can perform elevated actions silently. Unjustified privilege elevation; corporate IT security blocker. Rejected

Decision 6: First-Run Onboarding Wizard & Model Management

Approach Technical Concept Pros & Strengths Cons & Trade-Offs Verdict
Option A: Terminal Prompt Prompt user in console before launching window. Simple text code. Breaks desktop GUI immersion; confusing for non-technical users. Rejected
Option B: 3-Step Webview Wizard In-app modal: 1. Environment, 2. Opt-in models with SSE progress, 3. Role. Zero forced downloads; skip button for existing files; live download progress. Requires authoring modal components and SSE download endpoint. Selected
Option C: Settings Store Catalog Drop user into blank chat; hide models in settings. No modal overlay needed. High cognitive friction; leaves first-time user stranded with non-working chat. Rejected

4. Implementation Phasing & Task Dependency Structure

Work is organized into six strictly ordered tiers to prevent rework and guarantee continuous stability:

  • Phase 1: Foundation, Storage & Manifest Compliance: AppData directory resolution, Win32 manifest, single-instance mutex, and rolling disk logging.
  • Phase 2: Security Hardening & Secret Cryptography: CSPRNG token generation, localhost origin locking, and DNS rebinding host guard.
  • Phase 3: Kernel Job Trapping & Window Lifecycle: SafeProcessJob integration in desktop binary and Edge window supervisor watchdog.
  • Phase 4: Air-Gapped Network & Systems Hardware: Native Win32 adapter enumeration and typed ARP neighbor discovery.
  • Phase 5: Self-Bootstrapping Engine, Zero-Forced Downloads & Onboarding Wizard: Autonomous dependency verifier, SSE downloader API, bundled offline UI assets, atomic chat persistence, and the 3-step Kimi dark matte wizard.
  • Phase 6: Distribution Packaging & Verification Gate: Inno Setup installer script with clean uninstallation, full test suite validation, and release sign-off.
