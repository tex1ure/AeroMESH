AeroMESH: a zero-weight pipeline-parallel LLM cluster for consumer laptops

Two ordinary laptops split a 14B model's layers between them. Each keeps its own copy of the GGUF file on disk, so no model weights cross the network. Per token, only one INT8-quantised hidden-state vector (~5 KB) travels between the machines.

1. The problem and the answer

A 14B model at 4-bit needs roughly 9 GB of VRAM; typical gaming laptops have 6–8 GB.

Speaker noteOpen with the VRAM ceiling, then explain why the usual fix (tensor parallelism) cannot work over Wi-Fi.
"Two bottlenecks: the memory on each device, and the bandwidth between them."

❌ Why existing approaches fail

  • Tensor parallelism (Megatron, vLLM) synchronises inside every layer and needs NVLink/InfiniBand-class links.
  • Stock llama.cpp RPC ships weights over the network at start-up and sends uncompressed activations.
  • Consumer networks drop packets and change IPs; naive RPC stalls or crashes.

✅ What AeroMESH does

  • Local slices: each node memory-maps only its own layers from a local GGUF slice.
  • Pipeline parallelism: Node A runs layers 0..22, Node B runs 23..47 plus the LM head.
  • INT8 per-row activations: 5,124 bytes instead of 20,480 for d=5120.
  • Tailscale/WireGuard mesh with bounded frames, handshake auth and reconnect logic.

2. System architecture

Three tiers: browser + Python gateway, Rust coordinator (Axum), Rust worker over the mesh.

Speaker noteWalk left to right: browser → FastAPI :7860 → Axum :8080 → Stage 1 on GPU A → AERO frame over the mesh → Worker :50052 → ATOK reply → loop.

🛡️ Process containment (Windows)

SafeProcessJob in job_object.rs puts child processes in a Win32 Job Object so they die with the coordinator, freeing VRAM:

// job_object.rs · SafeProcessJob::new()
let mut info: JOBOBJECT_EXTENDED_LIMIT_INFORMATION = unsafe { std::mem::zeroed() };
info.BasicLimitInformation.LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE;

⚡ Shared-memory transport

For single-machine runs there is a shared-memory path, ShmPipelineTransport (aeromesh-core/src/transport.rs) backed by a ring buffer in shm.rs (tests: test_shm_ring_buffer_spsc, test_shm_ring_buffer_rejects_oversized_len). It is the fallback when no second laptop is available (.\start.ps1 all).

4. Wire protocol

All multi-byte header fields are big-endian. The INT8 row scale is little-endian.

Speaker noteReviewers like byte-level detail. Point out that the header's payload length must equal what S, d and dtype imply, or the frame is rejected before allocation.

Quantisation (as implemented)

scale = max_abs / 127.0        // scale = 1.0 if max_abs ≤ 1e-12
q     = clamp(round(x / scale), -127, 127) as i8
row   = [scale: f32 LE (4 B)] [q: i8 × d]

CRASH-01Dangling native pointers after a model switch

fixed in df93496 · slice_loader.rs, pipeline.rs, server.rs · test: test_closed_instance_safety, test_switch_model_invalid_path_preserves_old_model

Switching models freed the C++ context but left vocab dangling; the next tokenise call could crash the process with an access violation.

BeforeNo readiness check before FFI calls; pointers not cleared on close.
Afterclose() nulls every pointer; every FFI entry calls ensure_ready(); model switch keeps the old model if loading fails.
// slice_loader.rs
pub fn ensure_ready(&self) -> Result<()> {
    if !self.is_ready() { bail!("LlamaPipelineInstance is not ready or has been closed (native C++ pointers are null)"); }
    Ok(())
}

CRASH-02Arithmetic underflow in the GGUF slicer

fixed in df93496 · gguf_slicer.rs · test: test_slice_gguf_no_underflow_panic

An unflushed writer reported length 0, then len() - 24 underflowed and panicked on every slice. Replaced with explicit stream-position tracking and a static zero buffer for alignment padding.

FIX-05Unbounded allocation from the wire (remote DoS)

fixed in 521b3f0 · activation.rs · tests: …rejects_oversized_payload_ceiling, …mismatched_payload_bytes, …integer_overflow

Frames used the sender's length to allocate memory. Now: 128 MB payload ceiling, caps on sequence length (131,072) and hidden dim (65,536), and the header's payload length must equal the size implied by S, d and dtype (computed with checked multiplication). Handshake strings are length-capped too.

8. Deliberate constraints

Documented in LIMITATIONS.md and the status tracker as accepted decisions, not oversights.

Two-node topology

The target case is two laptops pooling VRAM. N-stage pipelines are future work (FIX-28).

Windows-first

The intended hardware is NVIDIA gaming laptops on Windows 11; Job Objects guarantee clean teardown (FIX-29).

No Docker

GPU passthrough on Windows is brittle; native PowerShell launch avoids it (FIX-30).

No TLS on localhost

Inter-node traffic rides WireGuard; loopback UI/API traffic is not encrypted (FIX-23).

Stateless engine

Chat history lives in the browser, as with llama-server (FIX-20).

Desktop-first UI

Optimised for a presentation/telemetry screen, not mobile (FIX-26).

9. Likely reviewer questions

Click a question to expand.

Why pipeline parallelism instead of tensor parallelism?

Tensor parallelism synchronises inside every layer, so it needs very high-bandwidth links. Pipeline parallelism synchronises once per token at the split point, so ~5 KB over Wi-Fi is enough.

What if the worker drops mid-generation?

The coordinator has bounded socket waits and a reconnect path for the worker transport; the failure surfaces as an error on the stream rather than a hang. For a permanent loss, run single-machine with .\start.ps1 all (shared memory).

Does INT8 activation quantisation hurt output quality?

Scales are computed per token row, which handles outliers better than a global scale. BENCHMARKS.md reports cosine similarity above 0.9995 against FP32 at the boundary. We have not run a full perplexity benchmark.

Why pre-sliced files on both laptops?

Slicing is a one-time step (gguf_slicer.rs); after that, start-up is an mmap, with no weight transfer on the network.

How are malicious peers handled?

WireGuard identity at the network layer; a 32-byte shared secret in the v3 handshake; v2 and malformed frames are refused; payload size is bounded and cross-checked before allocation.

Why a custom engine rather than llama.cpp RPC?

The engine adds INT8 activations, session/KV flags, authenticated handshakes, an OpenAI-compatible API with validation and rate limits, and Windows process containment. It still uses llama.cpp for the actual layer compute.

What changed after 11 Sep?

Crash fixes (CRASH-01/02, FIX-05), authentication (FIX-03), CORS (FIX-11), rate limits (FIX-08), validation (FIX-06/07/24), Stop button (FIX-19), gateway hardening (FIX-16), CI and documentation, then the October demo assets and Liquid Glass UI. See the ★ section.

Is 1.4 tok/s usable?

It is a feasibility result: the model does not fit one 8 GB GPU at all. Most of the per-token time is compute (~680 of ~710 ms), not network, so faster GPUs or a better split would help directly.
